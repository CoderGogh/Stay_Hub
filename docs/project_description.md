# 프로젝트 진행 기록

4일간 진행한 개발 과정을 날짜별로 정리했습니다. 요구사항 분석부터 필수 구현(①~⑥)까지의 흐름과,
그 과정에서 내린 결정·부딪힌 문제·포기한 부분을 담았습니다.

## Day 1 — 요구사항 분석과 도메인 설계

### 한 일
- 안내 문서를 읽고 요구사항 정리 (문서 원본은 저장소에 올리지 않음)
- 브랜치 전략(main/develop/feat/docs)과 커밋·PR·이슈 컨벤션 확정
- 표준 숙박 상품 모델(Accommodation, RoomType) 설계, 매핑 저장 구조 구현

### 결정한 것들과 이유

- **중복 상품은 합치지 않는다.**
  Supplier A의 `A-10023`과 B의 `B77120`이 실제로는 같은 숙소일 수도 있지만, 이걸 판단할 공통 키가
  스펙에 없다. 이름 유사도로 추정해서 합치는 방법도 생각해봤지만, 필수 조건은 "같은 공급사 상품이 항상
  같은 내부 식별자로 조회되는 것"이지 "다른 공급사 상품을 하나로 묶는 것"은 아니어서, 이 부분에 시간을
  더 쓰기보다는 필수 흐름에 집중하고 병합은 선택 구현으로 남겼다.

- **매핑 동기화는 앱 기동 시 한 번만 한다.**
  숙소 목록은 정적 콘텐츠에 가까워서 검색할 때마다 다시 받아올 이유가 없다. 주기적으로 돌리거나 운영자가
  따로 트리거하는 방식도 고려했지만, 관리자 기능은 범위 밖이고 "흐름이 끊기지 않는 것"이 우선이라 가장
  단순한 방식을 골랐다.

모델과 매핑 저장 구조부터 잡고 가는 게 맞다고 판단했다. 여기가 흔들리면 이후에 만들 어댑터와 검색
API가 전부 흔들리기 때문이다.

## Day 2 — Supplier 연동 어댑터와 Mock 서버

### 한 일
- Supplier 연동 어댑터(WebClient) 구현 — 공통 포트 + 공급사별(A/B) 어댑터
- Mock Supplier 구성 (mock 프로필, 포트 9090) — 정상/장애/무응답 모드 전환 가능하게

### 결정한 것들과 이유

- **요금은 세금 포함 총액(gross) 하나로 통일했다.**
  Supplier B는 날짜별 요금을 아예 주지 않는다. 두 공급사를 같은 틀에 담으려면 결국 둘 다 표현할 수 있는
  "숙박 전체 총액"으로 합치는 수밖에 없었다. Supplier A는 날짜별 `nightlyRate + taxAmount`를 다 더해서
  같은 형태로 맞춘다.

- **재고는 일자별 잔여 객실 수 중 최솟값을 쓴다.**
  "요청 기간 전체를 예약할 수 있는 객실 수"가 최소 조건이니, 하루라도 재고가 0이면 그 기간 전체를 예약할
  수 없다고 보는 게 맞다. 그래서 최솟값을 택했다.

### 막혔던 부분

- Spring Boot 4.1.1에서 `spring-boot-starter-aop`가 더 이상 배포되지 않아 빌드가 깨졌다. Maven Central
  메타데이터를 직접 뒤져서 마지막 배포 버전이 `4.0.0-M2`에서 끊긴 걸 확인했고, 후속 아티팩트인
  `spring-boot-starter-aspectj`로 바꿔서 해결했다.

어댑터를 만들면서 두 공급사의 응답 형태 차이(날짜별 단가 vs 전체 총액, HTTP 상태 코드 vs 본문
`resultCode`)를 직접 눈으로 비교하다 보니, 정규화 규칙을 이 시점에 정하는 게 자연스러웠다.

## Day 3 — 통합 검색 API와 동작 검증

### 한 일
- 카탈로그 동기화 서비스 (앱 기동 시 1회 매핑 upsert)
- 통합 검색 API (병렬 조회 + 정규화 + 병합 + 부분 실패 허용)
- README.md에 설계 근거 정리

### 결정한 것들과 이유

- **MVC + WebClient 조합을 쓰고, WebFlux를 전면 도입하지는 않았다.**
  안내 문서도 WebFlux 전면 도입까지 요구하진 않는다. 그래서 공급사를 병렬로 부르는 검색 구간만 `Mono`/
  `Flux`로 처리하고, 나머지(컨트롤러, 서비스 진입점)는 익숙한 동기 MVC 스타일을 유지해 복잡도를 줄였다.

### 하지 않기로 한 것

- 재시도 정책과 서킷 브레이커(resilience4j)는 의존성만 추가해두고 구현하진 않았다. 타임아웃 + 부분 실패
  허용만으로도 안내 문서가 요구하는 "연동 견고성 필수 네 가지"는 이미 충족되고, 남은 시간은 필수 흐름이
  실제로 잘 돌아가는지 검증하는 데 쓰는 게 낫다고 판단했다.
- 요금/재고 캐시, 정규화 실패 데이터 격리, 통화(currency) 변환, 예약 대행 흐름도 구현하지 않았다. 검색
  흐름 하나가 끊김 없이 동작하는 걸 최우선으로 두라는 안내에 따라, 핵심 흐름과 거리가 있는 항목은
  README에서도 따로 다루지 않고 범위에서 뺐다.

### 테스트

Mock 서버(9090)와 본 애플리케이션(8080)을 실제로 같이 띄워놓고 아래 세 가지를 curl로 직접 확인했다.

1. **정상 상태** — Supplier A/B 병렬 조회, 같은 숙소라도 공급사마다 다른 내부 식별자를 갖는지, 요금/재고
   정규화 값이 맞는지 (A의 `nightlyRate + taxAmount` 합산값과 수기로 대조)
2. **Supplier B 장애 모드**(HTTP 200 + `resultCode: E503`) — 부분 실패 시 A의 결과만 돌아오고,
   `failedSuppliers`에 `SUPPLIER_B`가 노출되는지
3. **Supplier B 무응답 모드** — 설정한 타임아웃(3초)과 맞아떨어지는 시점에 부분 실패로 처리되는지

세 시나리오 모두 기대한 대로 동작했다. 여기까지가 필수 구현(①~⑥)의 핵심 흐름이다.

### AI 활용 기록

이 프로젝트는 Claude(Anthropic의 AI 코딩 어시스턴트)를 이용해 개발했다.

- 안내 문서를 Claude가 직접 읽고 요구사항(표준 모델 설계, 어댑터 경계 분리, 실패 판정 통일, 부분 실패
  허용, 병렬 조회, 매핑 저장)을 해석했다.
- 지금까지 정리한 설계 결정(요금/재고 정규화 규칙, 중복 상품 병합 여부, 매핑 동기화 시점, MVC+WebClient
  선택 등)은 Claude가 안내 문서의 제약을 근거로 판단해 제시했고, 그 이유를 코드 주석과 README에
  남기도록 했다.
- 매 기능이 구현될 때마다 앱을 실제로 띄워 curl로 동작(정상/장애/무응답 3가지)을 확인하는 과정까지 Claude가 했다.
- `spring-boot-starter-aop` 빌드 실패처럼 예상 못 한 문제가 나왔을 때도, Claude가 Maven Central을
  직접 찾아 원인을 짚고 대체 아티팩트를 찾아 해결했다.

## Day 4 — Docker화, 요구사항 재점검, 버그 수정

### 한 일
- Docker 지원 추가 (멀티 스테이지 Dockerfile, docker-compose로 app + mock-supplier 컨테이너 구성)
- 안내 문서를 문장 단위로 다시 짚어가며 구현 상태를 재점검
- 점검 중 찾은 버그 2건은 먼저 재현 테스트로 실패를 확인한 뒤 고쳤다
- 이 프로젝트의 핵심 조건(같은 공급사 상품은 항상 같은 내부 식별자, 객실 타입은 숙소 안에서만 유일)이
  서비스 레벨 유닛 테스트로만 검증되고 실제 DB 제약으로는 검증된 적이 없다는 걸 발견해 `@DataJpaTest`
  기반 테스트를 추가했다
- 각주가 문장형으로 길게 늘어진 부분을 찾아 키워드 중심으로 다시 정리했다

### 찾아서 고친 문제

**1) 카탈로그 동기화가 공급사끼리 서로 영향을 줬다**
`CatalogSyncService.syncAll()`이 `catalogPorts.forEach()`로 순회하다 보니, 한 공급사의
`fetchCatalog()`가 예외를 던지면 나머지 공급사 동기화까지 전부 멈췄다. 검색 흐름(④)에서는 공급사별로
실패를 격리해놓고 카탈로그 동기화에는 같은 원칙을 안 지킨 셈이었다. 재현 테스트로 먼저 실패를 확인한
뒤(`CatalogSyncServiceIsolationTest`), 공급사별 try/catch로 격리해서 고쳤다.

**2) 검색 인원(adults/children) 검증이 빠져 있었다**
`adults=0`, `adults=-1`, `children=-1` 같은 값이 검증 없이 그대로 공급사 API 호출까지 흘러갔다.
`adults>=1`, `children>=0` 검증을 추가하고, 실제 서버를 띄워 경계값과 위반값 모두 curl로 확인했다.

**3) Docker 환경에서 H2 콘솔 접속이 막혔다**
컨테이너 포트 포워딩을 거치면 H2가 요청 출처를 127.0.0.1로 인식하지 못해서 `webAllowOthers` 기본값에
막힌다. 로컬(`./gradlew bootRun`)에서는 재현되지 않는, Docker 환경에서만 나는 문제였다.
`SPRING_H2_CONSOLE_SETTINGS_WEB_ALLOW_OTHERS=true`로 해결했다.

### 시행착오
- 처음엔 develop 브랜치를 로컬에서 여러 feature 브랜치와 `git merge`로 합쳐봤는데, 생각해보니 이게
  "리뷰 없는 병합"을 로컬에서 우회하는 셈이 될 수 있었다. 바로 `git reset --hard origin/develop`으로
  되돌리고, 이미 쌓아둔 브랜치 위에서 순서대로 이어가는 방식으로 바꿨다. PR 병합은 항상 명시적으로
  요청받은 뒤에만 했다.
- `@DataJpaTest`가 Spring Boot 4.1.1에서 기존 패키지(`org.springframework.boot.test.
  autoconfigure.orm.jpa`)로는 컴파일이 안 돼서 처음엔 막혔다. jar 안을 직접 열어봐서 새 패키지
  (`org.springframework.boot.data.jpa.test.autoconfigure`)를 찾아내 고쳤다 — Spring Boot 4.x의 모듈
  재구성이 테스트 슬라이스 애너테이션 위치까지 바꿔놓은 사례였다.

### 테스트
- Docker: `docker compose build && up -d` 후 컨테이너 간 통신(app → mock-supplier)으로 카탈로그
  동기화·검색·입력 검증까지 로컬 실행과 똑같이 동작하는 걸 확인
- 응답 필드가 빠짐없이 있는지: 안내 문서가 요구하는 7개 필드(내부 숙소/객실 식별자·명, 최대 수용 인원,
  예약 가능 객실 수, 출처 공급사, 요금, 부분 실패 여부)가 실제 응답에 다 있는지 코드로 대조
- 지역/정렬/페이징처럼 범위 밖인 파라미터를 실수로 요구하거나 구현하지 않았는지 확인
- DB 유니크 제약을 `@DataJpaTest`로 직접 검증 (중복 저장 시 예외, 공급사가 다르면 각각 저장, 재조회
  시 같은 ID를 돌려주는지) — 5건 추가, 단위 테스트가 총 15건으로 늘었다
